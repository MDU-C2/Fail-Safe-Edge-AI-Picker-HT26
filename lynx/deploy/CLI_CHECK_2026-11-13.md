### Why the unchanged startup guard now passed

Earlier attempts correctly stopped before loading the model with only
**117.0 MiB**, **121.7 MiB**, and **121.2 MiB** of visible shared headroom. The
required **128 MiB was not lowered**.

The successful prototype advised the OS that clean cache pages for **300 loaded
Python source/cache files**, totaling **5,553,599 file bytes**, were no longer
needed, then attempted glibc heap trimming. Files were not deleted, and no
captures, placement records or recovery state were cleared. Shared charge
around the cache-advice step changed from **139,481,088** to **129,990,656 bytes**.
That observed 9,490,432-byte decrease includes a changing shared environment;
it is not a precise attribution of reclaimed source-cache bytes. Heap trimming
reported released pages without claiming a byte amount. The subsequent actual
memory check passed at **130.5 MiB**.

The final 0.2.4 startup path also allows **up to five seconds** for a measured
headroom shortfall to recover, polling every 0.2 seconds against the unchanged
128 MiB requirement. No model is started during this wait. Unknown hierarchy
or unreadable counters fail immediately. This bounded wait does not reserve
memory or guarantee that future startup attempts will pass.

Evidence: `target-cache-camera-check.log` in the development
`tmp/lynx-cli-20261113` directory, plus the earlier `target-camera-check.log`,
`target-final-camera-check.log` and `target-trim-camera-check.log`. The target
retains captures under `/state/cli-0.2.0`; `camera-check-resources.json` is updated
by later checks, so the development logs retain the distinct run measurements.
